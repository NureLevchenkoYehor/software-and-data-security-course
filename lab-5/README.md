# Лабораторна робота №5. Реалізація платіжної форми веб-сайту

## Мета роботи

Вивчити можливості використання криптографічних функцій для перевірки справжності 
проведеної оплати пластикової карти в електронному магазині.

## Порядок роботи

Послідовно, протягом відведеного розкладом занять часу, відпрацювати такі питання:
1. Вивчити теоретичний матеріал.
2. Виконати вправи з практичної частини роботи для свого варіанту.
3. Оформити звіт з лабораторної роботи і захистити його.

## Теоретичні відомості

Приклад платіжної форми представлено в наступному коді:

```html
<form method="POST" action="https://www.liqpay.com/api/pay">

  <input type="hidden" name="currency" value="UAH" />

  <input type="hidden" name="language" value="ru" />

</form>
```

### Налаштування Stripe Sandbox

Для виконання лабораторної роботи було підготовлено ізольоване тестове середовище
платіжної системи Stripe:

1. **Реєстрація та активація Sandbox.** Створено обліковий запис у Stripe Dashboard і
   активовано ізольоване тестове середовище (Sandbox), яке повністю відтворює
   поведінку реальної платіжної системи без списання коштів.

2. **Отримання ключів API.** У панелі Stripe Dashboard (в межах обраного Sandbox)
   скопійовано публічний (`pk_test_...`) та секретний (`sk_test_...`) ключі для
   подальшої інтеграції клієнта та сервера.

3. **Встановлення Stripe CLI.** На робочій системі (CachyOS) інстальовано утиліту
   командного рядка `stripe` за допомогою менеджера пакетів та виконано авторизацію
   через `stripe login` із вибором режиму **sandbox**.

4. **Отримання секрету вебхуків.** За допомогою `stripe listen` згенеровано секрет
   підпису вебхуків (`whsec_...`) та підтверджено, що він залишається незмінним у
   межах активної пісочниці.

5. **Прийнято рішення** приймати події локально через `stripe listen --forward-to`
   замість реєстрації публічного HTTPS-ендпоінту, а всі три ключі зберігати статично
   у файлі `.env`.

### Платіжна форма та ініціалізація PaymentIntent

Платіжна форма реалізована відповідно до сучасної архітектури Stripe через
**PaymentIntents API** та **Payment Element** замість прямої передачі реквізитів
картки на сервер магазину.

Процес ініціалізації оплати відбувається у два кроки. По-перше, користувач обирає
товар у клієнтському інтерфейсі (форма `OrderCreationCard`) та натискає кнопку
«Створити замовлення». Браузер надсилає POST-запит до ендпоінту
`POST /api/orders/payment-intent` з описом замовлення та сумою (у мінімальних
одиницях валюти — центах або копійках). Бекенд фіксує замовлення зі статусом
`pending` у In-Memory сховищі (`InMemoryOrderStore`), викликає
`stripe.PaymentIntent.create(...)` з SDK, передаючи `order_id` у полі `metadata`
для подальшої ідентифікації у вебхуку, та повертає `client_secret` клієнту.

По-друге, отримавши `client_secret`, браузерна бібліотека `@stripe/react-stripe-js`
монтує компонент `<Elements>` та всередині нього — `<PaymentElement>`, який
завантажує захищену платіжну форму Stripe безпосередньо з інфраструктури Stripe.
Введені реквізити картки ніколи не передаються на сервер магазину. Натискання кнопки
оплати у компоненті `CheckoutForm` викликає `stripe.confirmPayment(...)` з
параметром `redirect: "if_required"` — підтвердження відбувається без перенаправлення
сторінки, якщо це не вимагається схемою 3DS.

```
Браузер                           FastAPI / store.py               Stripe API
   │                                     │                              │
   │  POST /api/orders/payment-intent    │                              │
   │       (amount, currency, desc)      │                              │
   │────────────────────────────────────>│                              │
   │                                     │  stripe.PaymentIntent.create │
   │                                     │─────────────────────────────>│
   │                                     │<─────────────────────────────│
   │                                     │  (id=pi_..., client_secret)  │
   │<────────────────────────────────────│                              │
   │  {client_secret, order_id}          │                              │
   │                                     │                              │
   │  stripe.confirmPayment()            │                              │
   │───────────────────────────────────────────────────────────────────>│
   │<───────────────────────────────────────────────────────────────────│
   │  {paymentIntent.status}             │                              │
```

### Обробник вебхуків та криптографічна перевірка Stripe-Signature

Після завершення обробки платежу Stripe надсилає сервер-серверне HTTP-сповіщення
(webhook) на ендпоінт `POST /api/webhooks/stripe`.

Критичною вимогою коректної перевірки підпису є зчитування тіла запиту
**виключно як необроблені байти** (`raw_body = await request.body()`), без
будь-якого попереднього JSON-парсингу. Автоматичний парсинг тіла фреймворком
змінює байтовий вміст (пробіли, порядок ключів), що неминуче призводить до
розбіжності при обчисленні HMAC і відхилення будь-яких легітимних вебхуків.

Перевірка підпису виконується офіційним SDK (`stripe.Webhook.construct_event(...)`),
який реалізує алгоритм HMAC-SHA256:

1. Зі значення заголовка `Stripe-Signature` витягується мітка часу `t` та одне або
   кілька значень підпису `v1`.
2. Формується рядок `signed_payload = f"{t}.{raw_body}"`.
3. Обчислюється `HMAC-SHA256(key=STRIPE_WEBHOOK_SECRET, msg=signed_payload)`.
4. Результат порівнюється з кожним значенням `v1` із заголовка через захищене
   порівняння з постійним часом (`hmac.compare_digest`).
5. Перевіряється, що мітка часу `t` не старіша за допустиму межу (за замовчуванням
   300 секунд), що унеможливлює атаки повторного відтворення.

При невдалій перевірці ендпоінт негайно повертає статус `400 Bad Request`.

Після успішної верифікації обробник виконує ідемпотентне оновлення стану замовлення:
перед застосуванням будь-якої зміни перевіряється, чи не було вже зареєстровано
подію з таким `event_id` у словнику `_processed_events`. Якщо так — повертається
статус `200 OK` без повторної обробки.

При отриманні запиту ендпоінт читає тіло як сирі байти через `await request.body()` та
витягує значення заголовка `Stripe-Signature`. Виклик
`stripe.Webhook.construct_event(payload, sig_header, secret)` перевіряє підпис і
повертає розпарсований об'єкт події. При невдалій перевірці одразу повертається
`400 Bad Request`; при успіху — ідемпотентно оновлюється статус замовлення:
`payment_intent.succeeded` переводить його у `paid`, `payment_intent.payment_failed` —
у `failed`.

Перевірку виконано скриптом `backend/test_webhooks.sh` — чотири сценарії, кожен
із яких повинен завершитися відповіддю `HTTP 400`:

| № | Сценарій                               | Очікувано | Отримано                               |
|-:-|:---------------------------------------|:----------|:---------------------------------------|
| 1 | Відсутній заголовок `Stripe-Signature` | `400`     | `400 Missing Stripe-Signature header.` |
| 2 | Підроблене тіло                        | `400`     | `400 Invalid Stripe-Signature.`        |

=== 2. Forged / tampered body ===

=== 3. Modified Stripe-Signature ===
HTTP 400: {"detail":"Invalid Stripe-Signature."}
=== 4. Stale timestamp (t - 600s) ===
HTTP 400: {"detail":"Invalid Stripe-Signature."}

## Відповіді на контрольні питання

> 1. Поясніть поняття «банк-еквайєр» і «банк-емітент».

**Банк-емітент** — банківська установа, яка видала платіжну картку
покупцеві та несе відповідальність за виконання платежу від його імені. Саме
банк-емітент перевіряє наявність коштів на рахунку, авторизує транзакцію або
відхиляє її, а також захищає клієнта від несанкціонованих операцій.

**Банк-еквайєр** — банк, який обслуговує торговця (інтернет-магазин) і
забезпечує технічне підключення до платіжних систем. Еквайєр отримує запит на
оплату від платіжного шлюзу, передає його через міжнародну платіжну мережу до
банку-емітента, а після авторизації забезпечує зарахування коштів на розрахунковий
рахунок магазину.

> 2. Поясніть покроково схему купівлі товару в інтернет-магазині.

1. Покупець обирає товар і переходить до оформлення замовлення. Магазин через
   платіжний SDK (`stripe.PaymentIntent.create`) резервує транзакцію на боці
   платіжного провайдера та отримує `client_secret`.
2. Браузер клієнта завантажує захищену платіжну форму безпосередньо з
   інфраструктури платіжного провайдера та покупець вводить реквізити картки.
3. Браузер виконує `stripe.confirmPayment(...)`, що надсилає зашифровані дані
   картки напряму до Stripe, минаючи сервер магазину.
4. Stripe передає запит на авторизацію через міжнародну платіжну мережу (Visa,
   Mastercard) до банку-еквайєра, а той — до банку-емітента покупця.
5. Банк-емітент перевіряє автентичність, доступний баланс та обмеження і повертає
   рішення: `authorized` або `declined`.
6. Stripe надсилає серверу магазину криптографічно підписане вебхук-сповіщення
   (`payment_intent.succeeded` або `payment_intent.payment_failed`).
7. Бекенд перевіряє підпис (`Stripe-Signature`) та ідемпотентно оновлює статус
   замовлення у своїй базі даних.
8. Якщо оплату підтверджено, магазин починає виконання замовлення і сповіщає
   покупця електронним листом.

> 3. Як уникнути багаторазової покупки того самого товару?

Ідемпотентне опрацювання вебхуків є основним механізмом захисту від дублювання.
Stripe може надіслати одну і ту саму подію декілька разів у разі мережевих помилок
або тайм-аутів. Щоб запобігти повторному виконанню логіки (повторному списанню,
подвійному відправленню товару), бекенд зберігає унікальні ідентифікатори вже
оброблених подій (поле `event["id"]`) у сховищі `_processed_events`. Перед будь-якою
зміною стану перевіряється наявність `event_id` у цьому словнику: якщо подія вже
оброблялась, обробник повертає `200 OK` без повторних дій.

Додатково, для запобігання дублюванню самих платіжних намірів, кожному замовленню
присвоюється унікальний `order_id`, який передається в `metadata` при створенні
`PaymentIntent`. Якщо замовлення з таким ідентифікатором вже існує у сховищі,
ендпоінт `POST /api/orders/payment-intent` повертає `409 Conflict`.

> 4. Як можна дізнатися, що покупець купив товар або відмовився від покупки?

Основним механізмом є **вебхуки** (webhook) — асинхронні HTTP-сповіщення від
Stripe на ендпоінт сервера магазину. Stripe надсилає подію `payment_intent.succeeded`
у разі успішної оплати та `payment_intent.payment_failed` у разі відмови чи
технічної помилки. Поле `data.object.metadata.order_id` у тілі події дозволяє
однозначно ідентифікувати замовлення у базі магазину і оновити його статус.

Вебхуки є більш надійним підходом, ніж опитування клієнта (polling), оскільки деякі
схеми підтвердження платежу (наприклад, 3D Secure або банківські перенаправлення)
завершуються асинхронно — після того, як покупець закрив вкладку браузера.
Додатково, статус конкретного `PaymentIntent` можна в будь-який момент отримати
через `stripe.PaymentIntent.retrieve(id)` у синхронному режимі.

> 5. Які поля включає в себе форма платіжного серверу?

У реалізованому прототипі форма платіжного сервера (ендпоінт
`POST /api/orders/payment-intent`) приймає такі поля:

| Поле | Тип | Обов'язковий | Опис |
|------|-----|:---:|------|
| `amount` | integer | Так | Сума у мінімальних одиницях валюти (центи, копійки). Мінімум: 100 для USD/EUR, 2500 для UAH. |
| `currency` | string | Так | Код валюти: `usd`, `eur` або `uah`. |
| `description` | string | Так | Опис замовлення (1–255 символів). |
| `order_id` | string | Ні | Власний ідентифікатор замовлення (3–64 символи). Якщо не передано, генерується автоматично у форматі `ORD-XXXXXXXX`. |

Відповідь містить: `order_id`, `client_secret` (для монтування Payment Element),
`payment_intent_id`, `amount`, `currency`, `status`.

> 6. Яка різниця між тестовим та реальним режимом роботи платіжної системи?

На прикладі прототипу.

**Тестовий режим (Sandbox / Test Mode):**
- Усі операції є симуляцією — реальні кошти не переміщуються.
- Використовуються спеціальні тестові ключі API (префікс `pk_test_...` та `sk_test_...`).
- Платежі проводяться тестовими картками Stripe (наприклад, `4242 4242 4242 4242`
  для успішної оплати, `4000 0000 0000 0002` для відхилення).
- Вебхуки можна генерувати та перенаправляти локально через Stripe CLI
  (`stripe listen --forward-to ...`).
- Дані та події тестового середовища повністю ізольовані від production.
- Доступні розширені інструменти відлагодження, журнали запитів та можливість
  імітувати різні сценарії (3DS, відмова банку, тайм-аути тощо).

**Реальний режим (Live Mode / Production):**
- Операції є справжніми фінансовими транзакціями зі списанням коштів.
- Використовуються бойові ключі API (префікс `pk_live_...` та `sk_live_...`).
- Вебхук-ендпоінт реєструється у Stripe Dashboard з публічно доступною HTTPS-адресою,
  а секрет підпису (`whsec_...`) отримується з налаштувань зареєстрованого ендпоінту.
- Для доступу до live-режиму потрібне підтвердження особи та банківських реквізитів
  у Stripe.
- Будь-яка помилка в обробці вебхуків або перевірці підпису може призвести до
  реальних фінансових наслідків (незарахування оплати, подвійного списання тощо).
