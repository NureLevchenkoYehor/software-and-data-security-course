### Загальне пояснення реалізації

Просту поштову систему реалізовано з двох частин: сервера та клієнта.

**Сервер**: приймає листи, зберігає їх у базі даних SQLite та віддає 
користувачам за запитом.

**Клієнт**: працює з командного рядка й дозволяє надсилати листи,
переглядати вхідні й читати окремий лист.

**Шифрування**: виконується на стороні клієнта, за алгоритмом
«одноразовий блокнот». Текст листа перетворюється на байти в 
кодуванні UTF-8, після чого кожен байт поєднується операцією XOR з 
байтом ключа.

**Ключ**: створюється випадково, має ту саму довжину, що й
повідомлення, та зберігається у файл.

**Передача**: шифротекст кодується у Base64 і надсилається як тіло 
листа. Сервер зберігає лише зашифрований текст і ключа не знає. 
Для прийому листа, клієнт завантажує його із сервера. Якщо вказано
файл із ключем, тіло листа декодується з Base64 і дешифрується тією 
самою операцією XOR. Без ключа лист виводиться у зашифрованому вигляді.
Ключ потрібно передати отримувачу окремо від листа, оскільки сервер 
його не зберігає.

**Авторизація**: доступ до сервера захищено токенами. Адміністратор
має додавати користувачів командою add-user та передавати токен 
користувачу, який буде використано у клієнті для його передачі у 
заголовку Authorization. Це потрібно виключно для авторизації користувачів 
у системі та надання їм лише їх листів.

### Пояснення коду

Структура проєкту:

```txt
root/
├ doc/               // Методичні вказівки та звіти.
├ src/
│ ├ admin.py         // CLI інструмент адміністратора для реєстрації користувачів.
│ ├ client.py        // CLI клієнт користувача.
│ ├ config.py        // Глобальна мережева конфігурація для клієнта та сервера.
│ ├ db.py            // Інтерфейс взаємодії із базою даних.
│ ├ schemas.py       // Контракти API.
│ └ server.py        // Серверний застосунок поштового сервісу.
├ .env               // Глоабльні налаштування середовища.
├ .gitignore         // Ігнорування файлів бази даних.
├ README.md
```

У файлі `schemas.py` визначені API контракти, які використовуються сервером для 
формалізації параметрів ендпоінтів.

У файлі `db.py` визначені функції для взаємодії із базою даних, фікусючи 
підключення, ініціалізацію, шлях до файлу бази даних та SQL-запити.

Файл `admin.py` є CLI програмою, яку адміністратор може використати для реєстрації 
нових користувачів у поштовому сервісі.

Він використовується наступним чином:

```bash
python admin.py add-user <username>
```

Після успішного виконання, в терміналі буде відображено токен авторизації у 
поштовий сервіс для новоствореного користувача, який користувач може зберегти у 
`.env` файл або використати безпосередньо.

Файл `config.py` читає `.env` файл, додаючи визначені у ньому змінні середовища 
до поточного середовища та визначає глобальні мережеві налаштування. 

Файл `server.py` є серверним застосунком поштового сервісу. Він реалізований на 
базі FastAPI та надає такі ендпоінти:


| Метод | Шлях           | Призначення                               |
| :---- | :------------- | :---------------------------------------- |
| GET   | /messages      | Отримання списку усіх листів користувача  |
| GET   | /messages/{id} | Отримання листу для перегляду його вмісту |
| POST  | /messages      | Відправка листу визначеним отримувачам    |

Усі ендпоінти потребують авторизації із використанням токену, що було користувачу 
адміністратором.

Файл `client.py` є клієнтським CLI застосунком для відправки та читання листів. 
Він надає можливість генерувати ключі, шифрувати вміст листів перед їх 
відправкою, та дешифрувати отримані з серверу листи.

CLI інтерфейс реалізовано за допомогою `argparse`. Серед можливостей користувача 
можна виділити наступні можливості:

- Безпосереднє використання токена авторизації. Через збереження історії команд, 
  ця можливість не є рекомендованою для використання у реальних сценраіях.
- Вказання `.env` файлу, у випадку якщо його локація відрізняється від стандартної.
- Відправка листів (`send`) із використанням текстового редактора за замовчуванням 
  для формування всього листа (`--editor`) або файлів в якості тіла листа 
  (`--file`).
- Шифрування вмісту відправляємого листа (`--encrypt`) із генерацією ключа 
  `secret.key` та вказання шляху та назви ключа (`--gen-key-path`).
- Перегляд поштової скрині користувача у зворотному хронологічному порядку 
  (`inbox`) з можливістю вказання кількості листів.
- Перегляд вмісту листа (`read`) за його id (`--id`), з можливістю вказання ключа 
  для дешифрування його вмісту (`--key-file`).

Так як шифрування оперує бінарними даними, кінцевий результат кодується у Base64 
для зручного текстового представлення ключів та шифротексту, яке можна зберігати у 
звичайному текстовому  файлі, передавати через термінал чи JSON та прочитати без 
проблем із кодуванням символів.

Для кодування тексту листів використовується UTF-8, яке дозволяє використання, 
зокрема, символів кирилиці. Ключі та текст листів, закодовані у Base64 
представлення, кодуються у ASCII, що описує обмеження формату Base64 більш 
коректно, ніж UTF-8.

## Відповіді на контрольні питання

> 1. Що таке атака (криптоаналіз)?

Криптоаналіз — це наука (і сукупність методів) про розкриття зашифрованої 
інформації без попереднього знання секретного ключа.

Криптографічна атака — це практична спроба зловмисника (криптоаналітика) порушити 
захист криптосистеми, щоб отримати доступ до відкритого тексту, відновити ключ 
шифрування або підробити дані.

Залежно від кінцевої мети зловмисника розрізняють кілька рівнів успіху атаки (від 
найслабшого до найкритичнішого):

- Повне розкриття: зловмисник знаходить секретний ключ і може розшифрувати 
  будь-які перехоплені чи майбутні повідомлення.
- Глобальна дедукція: зловмисник знаходить альтернативний алгоритм, еквівалентний 
  розшифруванню без знання самого ключа.
- Локальна дедукція: зловмисник розшифровує лише одне конкретне перехоплене 
  повідомлення (або його частину), не маючи змоги розшифрувати інші.
- Інформаційна дедукція: зловмисник отримує лише часткову інформацію про ключ або 
  відкритий текст (наприклад, дізнається кілька бітів або визначає, чи два 
  шифротексти відповідають однаковому повідомленню).

> 2. Які вимоги існують до основних методів криптоаналізу, опишіть їх?

Під «вимогами» в теорії криптоаналізу мають на увазі вихідні дані (умови), які 
необхідні криптоаналітику для проведення конкретного типу атаки. Від того, скільки 
інформації доступно зловмиснику, виділяють 4 основні моделі (методи) атак — у 
порядку зростання вимог до вхідних даних (і, відповідно, зростання сили атаки):

1. Атака тільки на основі шифротексту (Ciphertext-only attack, COA)
    - Вимога: зловмисник має лише один або кілька перехоплених шифротекстів (і 
      знає алгоритм шифрування, згідно з принципом Керкгоффса).
    - Опис: найскладніший для криптоаналітика, але найреалістичніший на практиці 
      сценарій — достатньо просто прослуховувати канал зв'язку. Для успіху 
      зазвичай потрібен великий обсяг шифротексту, щоб застосувати частотний 
      аналіз або статистичні методи. Якщо шифр вразливий до такої атаки, він 
      вважається повністю непридатним.
2. Атака на основі відомого відкритого тексту (Known-plaintext attack, KPA)
    - Вимога: зловмисник володіє не лише шифротекстом, а й відповідним йому 
      оригінальним відкритим текстом (або хоча б його фрагментом — наприклад, 
      стандартними заголовками листів, форматами файлів чи відомими фразами).
    - Опис: маючи пару «відкритий текст — шифротекст», криптоаналітик намагається 
      вивести ключ (або частину ключа), щоб розшифрувати інші повідомлення, 
      зашифровані тим самим ключем.
3. Атака на основі обраного відкритого тексту (Chosen-plaintext attack, CPA)
    - Вимога: зловмисник має можливість самостійно обирати довільні відкриті 
      тексти, передавати їх на шифрування (наприклад, маючи тимчасовий доступ до 
      шифрувального пристрою або надсилаючи свої дані в систему) і отримувати 
      відповідні шифротексти.
    - Опис: значно потужніший метод, ніж KPA, оскільки аналітик може спеціально 
      підібрати тексти зі зручною структурою (наприклад, з мінімальною різницею в 
      один символ), щоб простежити, як змінюється шифротекст, і швидко вирахувати 
      ключ.
4. Атака на основі обраного шифротексту (Chosen-ciphertext attack, CCA)
    - Вимога: зловмисник має можливість підсовувати системі довільні шифротексти 
      та отримувати результати їхнього розшифрування (наприклад, маючи доступ до 
      дешифратора або експлуатуючи відповіді сервера про помилки формату — як-от 
      padding oracle attack).
    - Опис: аналізуючи, як система розшифровує спеціально сформовані блоки даних, 
      криптоаналітик відновлює секретний ключ. Найчастіше застосовується проти 
      асиметричних криптосистем (наприклад, RSA).

> 3. Опишіть алгоритм Цезаря.

1. Визначаємо значення зсуву, таке, модуль якого за кількістю літер у алфавіті не 
   рівний нулю.
2. Шифруємо. Для кожної літери тексту:
    1) Визначаємо позицію літери тексту у алфавіті.
    2) Додаємо зсув то значення з кроку 1.
    3) Беремо модуль значення з кроку 2 за кількістю літер у алфавіті, отримавши 
       позицію літери шифротексту в алфавіті.
    4) Записуємо літеру шифротексту.
3. Дешифруємо. Як шифрування, але на кроці 2 зсув віднімається (береться в 
   протилежному напрямку).

> 4. Опишіть алгоритм «одноразовий блокнот».

1. Визначаємо деякий випадковий ключ, що складається з літер алфавіту, такий, що 
   його довжина відповідає довжині тексту.
2. Шифруємо. Для кожної літери тексту:
   1) Визначаємо позицію літери тексту у алфавіті.
   2) Визначаємо позицію літери ключа у алфавіті.
   3) Беремо суму значень з кроку 1 та 2.
   4) Беремо модуль значення з кроку 3 за кількістю літер у алфавіті, отримавши 
      позицію літери шифротексту в алфавіті.
   5) Записуємо літеру шифротексту.
3. Дешифруємо. Як шифрування, але на кроці 3, замість суми, береться різниця.

> 5. Опишіть використання методу повного перебору для атаки на алгоритм Цезаря.

Припустимо, ми знаємо, що текст зашифровано шифром Цезаря та в чому полягає його 
суть. Тоді, метод повного перебору полягає у знаходженні такого значення зсуву, 
за якого обране слово буде розшифроване.

Якщо шифротекст складається із літер англійської мови, то він складається з 26
літер. Таким чином, усього є 25 можливих варіантів ефективних ключів.

Можемо взяти довільне слово з шифротексту. Скажімо, ми обрали слово довжиною у 5 
літер. Тоді, для перевірки зсуву, в найгіршому випадку, нам потрібно виконати зсув 
125 разів, якщо зсувати по одній літері.

Власне, саме тому було створено спеціальний інструмент, який базується на 
виставлені літер шифротексту у відповідному порядку та прокручуванні зовнішнього 
диску з отвором. Це дозволяє підбирати по 5 літер одночасно, зменшуючи кількість 
операцій зсуву до кількості літер у алфавіті.

> 6. Чому повний перебір не використовується при атаці на алгоритм шифрування 
>    «одноразовий блокнот»?

Через властивість цього шифрування, яку називають досконалою секретністю.

Для будь-якої пари відкритого тексту та шифротексту існує єдиний ключ, такий що 
шифрування відкритого тексту ключем дасть шифротекст.

Інакше кажучи, будь-яка літера алфавіту могла бути зашифрована будь-якою літерою 
алфавіту, незалежно від того, яка літера алфавіту була використана для шифрування 
такої ж літери відкритого тексту. Літери "А" на початку та в кінці слова можуть 
бути зашифровані різними ключами.

Таким чином, за умови вибору відповідних рівоймовірних ключів, розшифроване слово 
немає значення, так як його можна розшифрувати інакше, використовуючи інший ключ.
